# Agent & Contributor Guide

Instructions for any automated coding agent (and any human) working in this
repository. Read this first, then read `CLAUDE.md` if present locally for the
deeper project context. Follow these rules so parallel work stays consistent
and `main` stays green.

This is **Group 16**'s distributed chat application for the Distributed Systems
course (University of Stuttgart, SS26). A short summary of the system lives in
the README; the full task breakdown and who owns what is in
[`docs/team_plan.md`](docs/team_plan.md).

---

## 1. Golden rules

1. **One issue, one branch, one PR.** Never commit feature work straight to
   `main`. Create a branch per GitHub issue, open a PR, get it green, get it
   reviewed, squash-merge.
2. **Every feature issue ships with a test.** No PR closes a feature issue
   without at least one efficient test that exercises the new behaviour. CI
   runs the whole suite; a red `mvn verify` does not merge. See section 4.
3. **English everywhere.** Code, comments, Javadoc, commit messages, branch
   names, PR titles and bodies, issue text. The only bilingual file is
   `docs/team_plan.md`.
4. **Respect the frozen architecture.** Do not reintroduce designs the
   professor rejected (section 5).
5. **No machine-authored watermarks.** No "generated by" notes, no co-author
   trailers on commits, no AI attribution in code, commits, or PR text. Commits
   use the human committer's git identity.

---

## 2. Build, format, test

The project is Java 21 + Maven. Common commands (also wrapped in the `Makefile`):

| Task | Command | Make target |
|---|---|---|
| Compile + install, skip tests | `mvn -DskipTests install` | `make install` |
| Format check (Google Java Format) | `mvn spotless:check` | `make lint` |
| Auto-format | `mvn spotless:apply` | `make format` |
| Unit tests only (Surefire, `*Test`) | `mvn test` | `make test` |
| Format + unit + integration tests (the full gate) | `mvn -B verify` | n/a |
| Shaded fat-jar at `target/chatapp.jar` | `mvn package` | `make package` |

Always run `mvn -B verify` locally before opening a PR. If Spotless complains,
run `mvn spotless:apply` and commit the result.

CI runs the same chain as ordered stages (format check, then build the
fat-jar, then unit tests, then integration tests), so a failure points at the
exact stage. `mvn -B verify` reproduces all of it locally in one pass.

## 3. Branching, commits, PRs

### Branch naming
Branch off `main`, one branch per issue:

- `feat/<area>-<short>` for features (e.g. `feat/protocol-envelope`)
- `fix/<area>-<short>` for bug fixes
- `chore/<short>` for build/CI/tooling
- `docs/<short>` for documentation

### Commits
- Conventional Commits prefixes: `feat:`, `fix:`, `chore:`, `docs:`, `test:`.
- One logical change per commit. Keep messages in English, imperative mood.
- Reference the issue in the PR (use `Closes #N`), not necessarily every commit.

### Pull requests
- One PR per logical change. Title in Conventional-Commits style.
- The PR body states what changed and ticks off the issue's acceptance criteria.
- CI (`mvn -B verify`) must be green before merge.
- At least one other team member reviews; Robert reviews all technical PRs.
- Squash-merge into `main`. Do not self-close the issue before review; let
  `Closes #N` close it on merge.

### Stacked work
If your issue depends on another open PR, branch off that PR's branch and set
your PR's base to it, so the diff stays small. Retarget to `main` once the
dependency merges.

## 4. Testing policy

Tests are not optional and they are not an afterthought.

**Naming decides where a test runs.** Name unit tests `*Test` (Surefire runs
them in the fast unit stage). Name integration tests `*IT` (Failsafe runs them
in the integration stage, after the fat-jar is built). Getting this wrong makes
a JVM-spawning integration test run in the fast stage with no jar present.

- **Every feature issue** adds at least one test under
  `src/test/java/com/chatapp/...`, placed next to the area it covers
  (`protocol`, `discovery`, `election`, `heartbeat`, ...).
- Prefer **fast, deterministic** tests. Pure logic (for example
  `Election.pickLeader`) gets plain unit tests; use `@ParameterizedTest` with
  `@MethodSource` for table-driven cases.
- Protocol code gets **encode/decode round-trip** tests plus a
  **malformed-input** test (a bad message must never crash the receive loop).
- Network and failover behaviour gets an **integration test** (`*IT`) that
  spawns real JVMs via `ProcessBuilder` and asserts on observable behaviour or
  log lines. Keep these under ~30s and flake-free over repeated runs.
- An "efficient test" means it asserts the behaviour the issue promises and
  runs quickly in CI. A test that always passes regardless of the code is not a
  test.
- CI runs `mvn -B verify` on every push and PR; it is the enforcement point.

When you finish an issue, the acceptance criteria in its body are your test
checklist. If the issue lists an expected log line or a timing bound, assert it.

## 5. Architecture: what is fixed, what is forbidden

The design is final after the professor's review. Client-server with three
replicated servers and a single elected leader.

**Use these:**
- **Highest-ID-Wins** leader election (deterministic on the set of live IDs).
- **UDP broadcast** for dynamic discovery; **UDP unicast** for heartbeats.
- Heartbeats every **2 seconds**; a peer is declared dead after **6 seconds**.
- Plain **TCP** for the chat fan-out from leader to clients and for state sync.
- **Java stdlib** networking only (`java.net.DatagramSocket`, `Socket`,
  `ServerSocket`, `java.util.concurrent`). Jackson (JSON) and SLF4J/Logback
  (logging) are allowed; nothing else for coordination.

**Do not reintroduce (explicitly rejected):**
- LCR (Le Lann–Chang–Roberts) ring election.
- Vector clocks.
- Complex reliable ordered multicast.
- ZooKeeper, Akka, Spring, or any coordination middleware.

## 6. Conventions

- Package layout: `com.chatapp.{server,client,protocol,discovery,election,heartbeat,config}`.
- **Zero-config by default**: `java -jar chatapp.jar server` runs with no arguments and no env
  vars. The server detects its own LAN address (advertised host) and broadcast targets, generates a
  random id, and uses the default ports. Env vars (`LISTEN_HOST`, `LISTEN_PORT`, `DISCOVERY_PORT`,
  `BROADCAST_ADDR`, `SERVER_ID`, `CLIENT_NAME`) are **optional overrides** only, used by the dev
  runner and tests. Do not require any env var at run time, and never hardcode `localhost`.
- Shared constants (for example `HEARTBEAT_INTERVAL_S`) live in
  `com.chatapp.config.Config`.
- Structured logs: `key=value` pairs on every state change a viewer should see
  during the demo (`event=peer_discovered peer_id=...`,
  `event=leader_changed new_leader=...`).
- The single fat-jar `target/chatapp.jar` runs on every host (3 physical hosts
  on a LAN for the demo: no Docker, no VMs).
